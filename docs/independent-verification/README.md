**Status: PROPOSED collection protocol. Independent hardware replication is
NOT_RUN.** This directory does not contain a physical receipt, an executable
validator or new GPU harness behavior. [Issue #91](https://github.com/aien-dev/CUDApp/issues/91#issuecomment-6407638311)
owns this evidence work under [#88](https://github.com/aien-dev/CUDApp/issues/88).

The [agent prompt](AGENT_PROMPT.md) describes the remaining implementation.

## What the current evidence establishes

The immutable [teardown candidate receipt](../../evidence/speculation/release-candidate-teardown/receipt.json)
reports an owner-operated physical vector result for CUDApp
`2e2421694f6110bd84885ae0b2d3caf249809d34`, with compiler source
`omega-mv@d7390d88d07dbf48cfbb0583070599c350f814d3` and compiler SHA256
`9749f38841a55917d41924a68bce31463ec2339910bddd5e6cbf6ea4420551db`.
It records wrong-math and restored-program controls and a privately retained
syscall trace. It explicitly leaves a second person's or machine's hardware
rerun NOT_RUN. It does not qualify a later source revision.

The [native kernel description](../speculation/NATIVE-KERNEL.md) and
`native/nvrm/context.om`, `native/blackwell/vector.om` and
`native/blackwell/launch.om` expose the direct device-client and native
instruction path. Source inspection and artifact hashes are not independent
physical execution. A matching hash identifies bytes; a signature identifies
an attestation under a key. Neither proves that the attested event occurred.
NVIDIA open kernel modules and GSP firmware remain required. A runtime that
does not use CUDA userspace is not evidence that the toolkit is absent.

## Freeze the experiment before collecting results

An operator independent of candidate generation owns the challenge and records
their relationship to the author. Self-reported independence is not verified
independence. Document who reviewed it, what they checked, and remaining trust
assumptions. An agent reviewing source is not an independent hardware operator.
A second operator on the same machine is distinct from a second machine.

1. Clone the exact public candidate and compiler revisions into clean workspaces.
   Save the full Git SHAs, clean/dirty status and any patch bytes and hashes.
   Freeze the harness and oracle revisions too. A dirty build is a different
   candidate, not a result on the clean SHA.
2. Record tool versions, build environment and the complete source composition
   and build commands. Rebuild the pinned seed compiler using its repository's
   accepted path on the supported architecture. Compare its hash with an
   independently recorded expected digest, not a sidecar just regenerated by
   the same build. Never execute a failed or partial compile output.
3. Hash the source unit, executable, reviewed kernel variants, descriptor
   builder/template and invariant configuration. Repeat the build in a fresh output directory and
   report exact byte agreement or a diagnosed difference. A rebuilt compiler's
   fixpoint is not a proof of compiler correctness. Runtime descriptors and
   arguments contain fresh sizes and allocation addresses: hash their finalized
   bytes per arm after challenge selection/allocation and before submission.
   Bind them to the frozen builder and challenge, not a preselected address.
4. Run the repository's host suite and relevant native host tests. Capture every
   command and exit. x86_64 cross-compilation or interpretation is not native
   AArch64 execution. Do not replace architecture-specific barriers with no-ops.
5. Freeze the candidate digest before challenge generation. The operator chooses
   fresh unpredictable inputs and publishes a timestamped commitment to the
   exact input bytes and generation recipe before launch. The candidate author
   must not select, replace or learn the challenge in advance. Runtime inputs
   necessarily reach the candidate; expected outputs remain with the referee.
   Record that chronology and its witness, not just self-asserted timestamps.
6. Use an independently implemented CPU oracle in a separate process/workspace.
   It consumes the exact input bytes and emits every expected uint32 result
   under the documented wraparound semantics. Do not reuse the candidate's
   generator, result buffer, checker or lookup table as the sole oracle.
   Publish its source/provenance, versions, command, exits and output digest.

Start with the bounded vector addition already supported by the native path.
Do not substitute a full model, arbitrary shader or benchmark. Preserve the
existing refusal cases and supported size bounds. After freeze, the operator
chooses challenge sizes within those bounds, including tails and boundaries.
Rebuilding to bake fresh values into candidate code breaks the freeze; add
reviewed runtime input transport first instead.

## Existing harness seams and missing work

Reuse `tests/speculation/native-kernel-test.om`, `vector-checks.om` and
`vector-checks-test.om`. Today the main function uses fixed salts; expected
values are computed inside the same test process. Its checks cover every
logical result and up to 64 unused output words, but there are no unused tail
words at maximum capacity. These are useful regressions, not the independent
challenge/CPU-oracle protocol above.

Before a device run, extend that existing harness in seeded .om for external
input and output artifacts, separate reference comparison, and properly
allocated guards. Do not move pointers or enlarge allocations without review
of launcher bounds and admission. Add host refusals for malformed/truncated
inputs, wrong size/digest, stale outputs, missing writes and oracle tampering.
The withheld-submission control below is missing and must be implemented and
host-tested before use. No new permanent C implementation or foreign fallback.

## Physical run, only after admission

The issue, this document and a PR are not permission to open a device. Obtain
the existing owner reservation and safe admission for the named machine,
bounded allocation/workload and observation window. Leave the resident model,
other workers, gates, installed toolkit, driver and firmware untouched. If
safe admission or supported hardware is unavailable, record NOT_RUN or the
exact blocker and stop the dependent work.

Record OS/architecture, GPU model and PCI identity, public-safe stable device
identity, loaded driver version and GSP dependency. Keep private device IDs in
raw custody when necessary, with a reviewed stable public alias. Do not infer
a second machine merely from a different alias. Record approved memory/time
limits, pre/post health checks scoped to the reservation and cleanup outcome.
No private service URLs, prompts, model data or unrelated process listings.

For each arm, use fresh input/output allocations as supported, poison the
entire output, snapshot input and guard bytes, and retain full readback. Ensure
poison is independently chosen and checked by the referee not to equal that
element's expected output. Do not expose expected values through a reversible
poison pattern such as their bitwise complement. Preserve all failures and
attempts. Do not discard failed attempts or selectively repeat runs to report
only successes. Diagnose failures, retain all attempts and never reuse an
earlier successful buffer.

| Arm | Required observation |
| --- | --- |
| Correct kernel | Actual submission/completion and every output matches the separate oracle. Input bytes and allocation guards remain intact. |
| Wrong-math kernel | Reviewed mutation changes arithmetic only, not addressing, bounds or termination. Submission completes, the oracle rejects wrong results, and guards stay intact. |
| Restored kernel | Fresh correctly restored code and output buffers pass again; record code identities for both versions. |
| No submission | Initialize normally but do not enqueue GPU work and do not enter a wait that can never complete. Readback stays at the fresh poison, not the oracle result. Trace evidence contains no launch for this arm. |
| Guards | Before/after guards for each accessible allocation and unused output extent remain unchanged in every arm. Explicitly report inaccessible/uncovered regions; do not claim total memory safety. |

A wrong-math control must not send malformed opcodes, invalid pointers or a
hang to the device. A no-submission arm is not a timed-out GPU experiment.
Use the existing cleanup path; an uncertain device state requires the owner's
recovery procedure, not an agent-initiated reset or driver reload.

The external referee checks all output bytes, guards and expected failures.
Candidate stdout saying PASS is not the result. A host routine that writes the
expected outputs would pass arithmetic comparison; the dynamic observation,
no-submission control and independent review must address that alternative.
This remains scoped empirical evidence, not formal hardware attestation.

## Dependencies and observation

Keep separate inventories for build tools, optional test/oracle tools and the
runtime process tree. Record installed `nvcc`/toolkit separately from whether
any component was executed or loaded by the measured path. Do not claim
"toolkit absent" from a clean dependency scan. Testing absence requires a
separately approved environment; never uninstall software from the Spark.

Use the existing `make zero-cuda-gate` for its actual static ELF scope. Add
reviewed static inspection of the exact native ELF: headers, dynamic entries,
imports, interpreter, and build inputs. Static linking alone cannot exclude
embedded code, subprocesses or dynamic loading. Static output is one evidence
row, not a verdict about everything that could execute.

Collect full raw process/device-call logs across the relevant process tree,
including exec/load/open/ioctl/mmap/submission/completion and exits where the
observer supports them. The historical command was
`strace -f -o kernel-syscalls.log ./kernel.elf`; this is a reference, not an
authorized command to run now. Explain trace coverage and limitations rather
than claiming a tool decoded more than it did. Correlate buffers and commands
with the exact kernel/launch artifacts and the bounded readback. An ioctl or
an NVIDIA device open by itself does not establish the claimed computation.
Any profiler or observation tool is separately inventoried and admitted.

Record provenance and license obligations for the exact source/tool closure.
Unresolved current-tree licensing or vendor-listing questions belong to
[#89](https://github.com/aien-dev/CUDApp/issues/89); do not assert that the whole
tree has one license or change headers to make an audit appear clean. This
protocol does not authorize redistribution of material under review.

## Public evidence and raw custody

Create a new immutable `evidence/<run-id>/` bundle. Never rewrite the old
receipt. Save commands, start/end UTC, exit codes, stdout/stderr, full outputs,
input/oracle/kernel/launch digests, pre/post checks and all control failures.
For each artifact record byte count and SHA256. Publish source-owned artifacts
only; never add vendor binaries, firmware, cubins/PTX or vendor listings.

Before publishing, scan and manually review commands, logs, patches, device
identifiers and manifests for secrets and private information. Sanitization
must preserve evidence-bearing event order, operation/result fields and
consistent alias relationships. State every removed class and its effect on
verification. If critical evidence cannot be published, label that check
incomplete for public verification instead of hiding the limitation.

For every sanitized file, retain the raw original under authorized custody,
record both hashes, the transformation specification, reviewer, and access
conditions. Do not publish the private path. A raw hash is a commitment, not
access to the raw trace. If later confidential inspection is needed, seek
separate authorization; this protocol does not grant disclosure permission.

The operator writes a report naming what they personally rebuilt, generated,
observed and checked, their relationship to the author, and what remained
unobserved. A reviewer verifies identities, chronology, artifact bytes and
controls before accepting a narrow claim. Optional signatures cover exact
report bytes and key identity without introducing a new trust root or a
physical-proof claim. An optional separately admitted second-machine run gets
its own bundle and retains all platform differences.

## Manifest contract and review checklist

[manifest.NOT_RUN.json](manifest.NOT_RUN.json) is an empty **template**, not a
receipt. [manifest.schema.json](manifest.schema.json) uses JSON Schema draft
2020-12. A standard external validator can check its structure. This PR does
not add a validator dependency, CI acceptance gate or manifest consumer.

- `claim_status` is always `NOT_EVALUATED`. There is no automatic PASS value.
- Check statuses are NOT_RUN, BLOCKED, FAILED or COLLECTED. COLLECTED means
  evidence was attached, not that it is authentic, sufficient or successful.
- A template cannot carry commands, artifacts, identities, operator claims or
  a completed check. Never present generated schema-test data as run evidence.
- An operator report may be incomplete. Describe exactly why a row is missing;
  optional second-machine/toolkit-absent checks can remain NOT_RUN without
  inventing broader claims. Preserve failed observations as FAILED.
- Every command must identify its script/argv context, UTC times, exit status,
  and stdout/stderr artifact IDs. Timestamps use UTC `Z` with a lexical
  date/time range check, excluding leap seconds. Calendar validity needs a
  validator with date-time format support or a separate calendar check; the
  locally installed referee lacks that optional format checker. Public paths
  are bundle-relative, never
  private machine paths. The schema cannot sanitize free text for you.
- Review must resolve every referenced command/artifact ID, reject duplicates,
  verify every byte count/hash, chronology and identity against actual files,
  enforce admission and check semantics. JSON Schema does **not** perform
  these cross-record or physical checks. Self-filled fields are unverified.
- Hash/signature validity, schema validity, host tests and code review cannot
  be substituted for a hardware observation. Keep owner hardware, independent
  operator hardware, second-machine hardware, host and simulator claims apart.

The [host-only contract checks](../../evidence/independent-verification/host-contract-20261026/README.md)
record structural/refusal validation and unchanged repository test blockers.
